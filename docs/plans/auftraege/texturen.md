## Your topic: GPU-compressed textures (KTX2 / Basis Universal) – faster loading, far less memory on the iPhone
Falko asked for faster loading (23.10. 2:52: „schneller laden und testen“); the phase 2 plan names it (`docs/plans/plan_phase2.md`, building block 4). Measured today on the test machine (software rendering, `viz3/test/loadprof.py`): almost the whole start goes into uploading textures (`uploadTextures` / `initTexture` ~24–32 s for ~430 textures) and `applyTier` (~9 s). `viz3/test/texprobe.py` shows that 456 of 462 textures are used within 60 m of the garden – deferring them by distance would not help. On phones the decoded RGBA images are the memory problem (`viz3/test/memphone.py`: peak GPU memory ~1.3 GB on a first visit even with halved textures; Safari drops the page around 1 GB). The lever: GPU-compressed textures (KTX2 with Basis Universal, transcoded in a worker by three's KTX2Loader to BC7/BC1-3 on desktops, ASTC/ETC2 on phones) – about a quarter of the memory and far less upload work.
- Today: textures are loaded in `viz3/src/core/assets.js` (`TXL` TextureLoader / ImageBitmapLoader around line 300, `texFile`, `texUse`, `texFileOf`, the manifest `TEXMAN` written by the build, `TEXHALF` halves images ≥ 512 px on phones and quarters them after a broken-off attempt), the ground detail textures as one texture array in `viz3/src/core/detail.js` (DETAIL). The image files are not in the repo: the build (`viz3/build.py`, `viz3/buildlib/assets.py`) takes them from `viz3/dist/` (seeded from the published website `gh-pages`; `tex/*.webp|jpg`), see docs/WORKFLOW.md „Bauen“. three r169 ships `KTX2Loader` (`three/examples/jsm/loaders/KTX2Loader.js`) and the transcoder (`three/examples/jsm/libs/basis/basis_transcoder.js` + `.wasm`).
- Goal (in this order; report measurements after each step):
  1. **Encode**: a script `tools/tex/ktx2.py` (or .sh) that converts the site's textures to KTX2 with the KTX-Software tools (`toktx` / `ktx create`; get the Linux release from GitHub `KhronosGroup/KTX-Software` with `gh release download` – GitHub is reachable from this machine and from GitHub Actions): UASTC (with RDO/zstd) for normal and ORM maps, ETC1S or UASTC for colour maps (pick by quality/size – compare a few side by side), mipmaps generated, sRGB only for colour. Do it in a GitHub Actions workflow of your own (`.github/workflows/texturen-ktx2.yml`: workflow_dispatch + pushes to feat/texturen touching tools/tex/**) that publishes ONLY a new folder `tex2/` on gh-pages (same publishing pattern as `.github/workflows/welt-vessra.yml`: gh-pages concurrency group, retry/rebase, touch nothing else) – AND add `'tex2'` to the KEEP set in `viz3/deploy_site.py` so the site deploy keeps it (today it keeps only .git, plan.json, vorschau, welt-test), and make `live.yml` / the preview build copy it into dist like the rest of the site (check). Keep the folder well under 300 MB.
  2. **Load**: in `core/assets.js` load `tex2/<name>.ktx2` with KTX2Loader when the transcoder works (detectSupport with the renderer; the transcoder files copied into dist by the build), else the current webp/jpg (fallback per texture on any error); keep the texture parameters (wrap, repeat, rotation, anisotropy, colorSpace) and the manifest's tiling; on phones skip the top mip level instead of TEXHALF's canvas halving (or keep TEXHALF for non-KTX2 only); keep the shader programs the same (no new defines; a compressed texture must not change a material's program – check the program count). The DETAIL texture array may stay as it is in the first step.
  3. **Measure and compare**: start time (loadprof, softgl), memory (memphone: peak GPU/renderer MB, decoded texture MB), shader programs, and pictures before/after at the same views (garden, pavilion interior, village, forest – `viz3/test/realviews.py` or your own) – look at them with the Read tool; quality must stay good (normal maps without blocks, no colour shifts). Switch: `?tex2=0` turns it off for comparison.
